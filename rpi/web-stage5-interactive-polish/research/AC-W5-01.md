# Research: AC-W5-01 — Task completion animation + reduced motion fallback

## Understanding

When a user marks a task as done, three animations fire together:

1. **Checkmark draws in (0.3s)** — SVG path animates from hidden (stroke-dashoffset=24) to fully
   visible (stroke-dashoffset=0) using the `checkDraw` keyframe that already exists in globals.css.

2. **Card mutes (0.2s)** — The task row's opacity transitions to 0.7. This is already applied
   statically via `opacity-70` (Tailwind) when `isComplete` is true. The fix is adding
   `transition-opacity duration-200` to the row's transition classes so the change animates.

3. **Next task highlights (0.3s pulse)** — The first priority task that is NOT the just-completed
   task gets a brief background pulse to draw attention to what comes next.

**Reduced motion:** The global rule in globals.css already handles this:
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```
All three animations collapse to instant automatically. No JS branching needed.

**Framer Motion NOT needed** — pure CSS + Tailwind transitions are sufficient for all three
phases. Framer Motion adds ~30KB+ and should only be introduced if CSS cannot achieve the result.

**Timing context:** Completion is triggered from TaskDetail (`onComplete` prop). After
`handleComplete()` fires, `setSelectedTask(null)` navigates back to the list view. The animation
plays on the TaskRow as the user returns to the list — they see the checkmark drawing in and
the card settling to muted state.

## Functions / Routes / Tests

```typescript
// New state
const [justCompletedId, setJustCompletedId] = useState<string | null>(null)
const [nextHighlightId, setNextHighlightId] = useState<string | null>(null)

// In handleComplete, before optimistic update:
const nextTask = priorityTasks.find(t => t.taskId !== taskId)
setJustCompletedId(taskId)
setNextHighlightId(nextTask?.taskId ?? null)
// Clear both after animation duration (0.3s draw + margin = 600ms)
setTimeout(() => {
  setJustCompletedId(null)
  setNextHighlightId(null)
}, 600)
```

## Ambiguities / Questions

None identified. All three animation phases have explicit specs:
- Checkmark: 0.3s, `checkDraw` keyframe already exists
- Card mute: 0.2s, `opacity-70` + `transition-opacity`
- Next task pulse: 0.3s, new `taskHighlightPulse` keyframe
- Reduced motion: global CSS rule already handles it

The only interpretive call is "next task highlights" — the spec says "next task highlights
(0.3s pulse)." I interpret "next task" as the first item in `priorityTasks` (topThree) that
is not the task being completed. This is the most visible "next" task from the user's
perspective (it's in the "Do these first" section at the top of the list).
