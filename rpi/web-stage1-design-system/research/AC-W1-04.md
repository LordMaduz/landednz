# Research: AC-W1-04 — cn() utility at src/lib/utils/cn.ts

## Understanding

AC-W1-04 creates the `cn()` class merging utility that every UI primitive in Stage 1 will rely on.
`cn()` wraps `clsx` (conditional class logic) and `tailwind-merge` (conflict resolution) so that
callers can safely compose Tailwind classes without duplicate or conflicting utilities.

The verification test — `cn('px-4 py-2', 'px-8')` returns `'px-8 py-2'` — specifically exercises
tailwind-merge's conflict resolution: `px-8` wins over `px-4` because it appears last, and `py-2`
is kept intact since there's no conflict. This is the core value of tailwind-merge over plain clsx.

The utility is consumed by every UI primitive via `className={cn(...)}` patterns (see apps/web/CLAUDE.md).

## Functions / Routes / Tests

**cn.ts implementation:**
```typescript
import { clsx, type ClassValue } from 'clsx'
import { twMerge } from 'tailwind-merge'

export function cn(...inputs: ClassValue[]): string {
  return twMerge(clsx(inputs))
}
```

**cn.test.ts verification:**
```typescript
import { describe, it, expect } from 'vitest'
import { cn } from './cn'

describe('cn()', () => {
  it('merges class strings', () => {
    expect(cn('px-4 py-2', 'px-8')).toBe('px-8 py-2')  // AC spec verification
  })
  // Edge cases to also cover:
  it('handles conditional classes', () => {
    expect(cn('base', false && 'excluded', 'included')).toBe('base included')
  })
  it('deduplicates same utility', () => {
    expect(cn('text-body', 'text-body')).toBe('text-body')
  })
})
```
