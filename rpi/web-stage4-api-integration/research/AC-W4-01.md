# Research: AC-W4-01 — Google OAuth end-to-end on web, session persists on refresh

## Understanding

Wire the existing `AuthCard` Google button to real Supabase OAuth. The flow:
1. User clicks "Continue with Google"
2. Browser redirects to Google consent screen via `supabase.auth.signInWithOAuth()`
3. Google redirects to `/auth/callback?code=...` (Next.js route handler)
4. Callback route calls `supabase.auth.exchangeCodeForSession(code)` — sets HTTP-only session cookies
5. Browser redirects to `/roadmap` (or saved redirect path from query param)
6. On page refresh, session is read from cookies — user stays authenticated

The existing `middleware.ts` uses a naive `sb-*` cookie prefix check (stub from Stage 2).
This AC does NOT require upgrading the middleware — that's AC-W4-02. But the OAuth flow
will naturally set `sb-*` cookies so the Stage 2 middleware will correctly recognise the session.

## Constraints That Apply

- **CW06**: Auth session via Supabase SSR cookies ONLY. Never localStorage.
  `createBrowserClient()` handles cookies automatically. Do NOT store the session or access token in Zustand or localStorage.
- **CW01**: No raw values in components — env vars go in `.env.local`, not hardcoded.
- **CLAUDE.md known gotcha**: `@supabase/ssr` requires specific cookie setup for App Router middleware.
  The callback route uses `createServerClient()` which must use the `getAll`/`setAll` cookie pattern.

## Ambiguities / Questions

**Q1 — Does the OAuth callback need to call `POST /auth/verify`?**
The backend `POST /auth/verify` endpoint creates the user in Prisma DB (user upsert). The API's
protected routes (e.g. `GET /roadmap`) use an auth middleware that also upserts the user.
Question: should the web callback route call `POST /auth/verify` explicitly, or rely on the
first protected API call to create the user? If we call it in the callback, the user is
guaranteed to exist before onboarding. If we don't, a race condition is unlikely but
theoretically possible. Which approach does the spec prefer?

**Q2 — Redirect after OAuth: where exactly does the session token come from for the callback route?**
Standard Supabase PKCE flow: Google redirects to `/auth/callback?code=XXX`. The route handler
calls `exchangeCodeForSession(code)` which sets the session in cookies. This is the standard
pattern — confirming this is correct (not using implicit flow or token fragment).

**Q3 — The `redirect_uri` in `supabase/config.toml` is empty string.**
Google Cloud has `http://127.0.0.1:54321/auth/v1/callback` registered. Supabase handles the
OAuth handshake at its own endpoint, then redirects to the `redirectTo` option in
`signInWithOAuth()`. This is the standard PKCE flow. Confirming: the Next.js `/auth/callback`
route receives the code from Supabase (not directly from Google). Is this understanding correct?
