# Research: AC-W4-02 — Auth middleware redirects unauthenticated to `/auth/signin?redirect={path}`, returns to original path after sign-in

## Understanding

AC-W4-01 wired Google OAuth end-to-end. The middleware from Stage 2 is still using a naive
`sb-*` cookie prefix check (a deliberate stub — the comment in middleware.ts literally says
"Stage 4: replace with createServerClient().auth.getUser() from @supabase/ssr").

AC-W4-02 has two jobs:

1. **Upgrade middleware** — replace the `sb-*` cookie sniff with a real Supabase session check
   via `createServerClient().auth.getUser()`. This gives accurate authentication state and
   handles token refresh correctly.

2. **Return to original path** — currently the `AuthCard` hardcodes
   `redirectTo: ${origin}/auth/callback` without the `redirect` query param. So after OAuth,
   users always land on `/roadmap` regardless of where they started. The `redirect` param
   needs to flow: middleware → signin URL → AuthCard → callback URL → final redirect.

The `callback/route.ts` already reads `searchParams.get('redirect') ?? '/roadmap'`, so
it will work correctly once the `redirect` param is passed through the OAuth flow.

**The Supabase PKCE flow with custom params:**
Supabase preserves custom query params on the `redirectTo` URL. So if `redirectTo` is
`${origin}/auth/callback?redirect=/roadmap`, Supabase appends `code=XXX` and the callback
receives both `code` and `redirect` params correctly.

## Functions / Routes / Tests

### `middleware.ts` — upgrade session check

The middleware runs in Edge runtime. It CANNOT use `next/headers` (cookies() from next/headers).
Cookie handling must use `request.cookies` from NextRequest + `NextResponse`.

Pattern (from @supabase/ssr docs for Next.js middleware):

```typescript
import { createServerClient } from '@supabase/ssr'
import { NextRequest, NextResponse } from 'next/server'

export async function middleware(request: NextRequest) {
  let supabaseResponse = NextResponse.next({ request })

  const supabase = createServerClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      cookies: {
        getAll() {
          return request.cookies.getAll()
        },
        setAll(cookiesToSet) {
          cookiesToSet.forEach(({ name, value, options }) =>
            request.cookies.set(name, value, options),
          )
          supabaseResponse = NextResponse.next({ request })
          cookiesToSet.forEach(({ name, value, options }) =>
            supabaseResponse.cookies.set(name, value, options),
          )
        },
      },
    },
  )

  const { data: { user } } = await supabase.auth.getUser()

  const { pathname } = request.nextUrl
  const isProtected = PROTECTED_PATHS.some(
    path => pathname === path || pathname.startsWith(`${path}/`),
  )

  if (isProtected && !user) {
    const url = request.nextUrl.clone()
    url.pathname = '/auth/signin'
    url.searchParams.set('redirect', pathname)
    return NextResponse.redirect(url)
  }

  return supabaseResponse  // IMPORTANT: return supabaseResponse to preserve cookie refresh
}
```

Key: must return `supabaseResponse` (not `NextResponse.next()`) so that any session token
refresh cookies set by Supabase are forwarded to the browser.

### `AuthCard.tsx` — thread redirect param through OAuth

In `handleGoogleClick`, read the `redirect` param from the current page URL and include it
in the `redirectTo` so the callback route knows where to send the user after auth:

```typescript
const handleGoogleClick = async () => {
  setMode('google_loading')
  const supabase = createClient()
  const params = new URLSearchParams(window.location.search)
  const redirect = params.get('redirect') ?? '/roadmap'
  await supabase.auth.signInWithOAuth({
    provider: 'google',
    options: {
      redirectTo: `${window.location.origin}/auth/callback?redirect=${encodeURIComponent(redirect)}`,
    },
  })
}
```

## Constraints That Apply

- **CW06**: Auth state via Supabase SSR cookies only — `getUser()` reads from cookies.
  Never localStorage. The middleware upgrade is aligned with this constraint.
- **Edge runtime restriction**: `middleware.ts` runs in Edge runtime. Cannot import
  `next/headers`. Must use `request.cookies` / `NextResponse` for cookie access.
- **Return `supabaseResponse`**: If the middleware returns `NextResponse.next()` instead of
  `supabaseResponse`, Supabase cannot refresh expired tokens (session expires silently).
  Must always return `supabaseResponse` on the pass-through path.
- **Known failure point from spec**: `/auth/signin` must NOT be in PROTECTED_PATHS —
  already correct in current code, but must remain so to avoid infinite redirect loop.
