# Research: AC-W4-05 — Roadmap fetches from GET /roadmap, hero card correct counts, topThree correct

## Understanding

`RoadmapView` currently imports `MOCK_PHASES` and `MOCK_TASKS_FLAT` directly. This AC replaces
that with a real `GET /roadmap` call and passes the API data through.

This AC also fixes the broken user flow identified during AC-W4-04 verification:
- First-time user after OAuth lands on `/roadmap`
- Server fetches `GET /roadmap` → returns 404 (no profile)
- Page redirects to `/onboarding`
- After onboarding submits → `/roadmap` → now returns real data

**API response shape (`RoadmapResponse`):**
```typescript
{
  topThree: RoadmapTask[]    // top 3 non-complete, non-blocked tasks by priorityScore
  phases: RoadmapPhase[]     // all tasks grouped by phase number
  lastComputedAt: string     // ISO timestamp
}

RoadmapTask {
  taskId, name, phase, status, priorityScore,
  isBlocked, blockingTaskNames: string[],
  estimatedDuration, taskType ('FREE'|'PREMIUM'), consequenceLine
}
```

**API error behaviour:** 404 if no profile exists OR no roadmap entries.

**Key mapping challenges:**
1. `name` → `taskName`
2. `taskType === 'PREMIUM'` → `isPremium: boolean`
3. `cardState` derived from `status + isBlocked + taskType` (AC-W4-06 will unit-test this)
4. `blockingTaskNames: string[]` → `blockedBy.taskName` (first entry only — API gives names,
   not IDs; `blockedBy.taskId` will be empty string, only `taskName` used in `TaskRow` display)
5. `difficulty` — NOT in API response, will be `undefined` (field is optional in `TaskListItem`)
6. Phase names/timelines — NOT in API, derived from hardcoded constants in mapper

**Fetching strategy:** `page.tsx` becomes a server component. Gets Supabase session token
server-side, calls `GET /roadmap`, redirects to `/onboarding` on 404, passes data to
`RoadmapView` as prop.

## Functions / Routes / Tests

### `api.ts` addition

```typescript
export interface RoadmapApiResponse {
  topThree: RoadmapApiTask[]
  phases: { phase: number; tasks: RoadmapApiTask[] }[]
  lastComputedAt: string
}

export interface RoadmapApiTask {
  taskId: string
  name: string
  phase: number
  status: 'NOT_STARTED' | 'IN_PROGRESS' | 'COMPLETE'
  isBlocked: boolean
  blockingTaskNames: string[]
  estimatedDuration: string
  taskType: 'FREE' | 'PREMIUM'
  consequenceLine: string
}

export async function getRoadmap(token: string): Promise<RoadmapApiResponse> {
  const res = await fetch(`${API_URL}/roadmap`, {
    headers: { Authorization: `Bearer ${token}` },
    cache: 'no-store',
  })
  if (!res.ok) throw Object.assign(new Error('Roadmap fetch failed'), { status: res.status })
  return res.json()
}
```

### `page.tsx` (server component)

```typescript
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'
import { getRoadmap } from '@/lib/api'

export default async function RoadmapPage() {
  const supabase = createClient()
  const { data: { session } } = await supabase.auth.getSession()
  if (!session) redirect('/auth/signin?redirect=/roadmap')

  try {
    const data = await getRoadmap(session.access_token)
    return <RoadmapView initialData={data} />
  } catch (err: unknown) {
    if ((err as { status?: number }).status === 404) redirect('/onboarding')
    return <RoadmapView initialData={null} />  // error state — handled in AC-W4-14
  }
}
```

## Ambiguities / Questions

**Q1 — `blockedBy.taskId` is empty string:** API only gives `blockingTaskNames: string[]`.
`TaskRow` only uses `blockedBy.taskName` for display ("Needs: X"). Empty string for taskId
is acceptable for AC-W4-05. Confirmed: not needed for display.

**Q2 — Error state when API fails (non-404):** The spec says "error state" is in AC-W4-14.
For AC-W4-05, passing `null` as `initialData` and showing nothing (or leaving mock display)
is acceptable. AC-W4-14 will wire the proper error UI.

Both non-blocking. No human clarification needed.
