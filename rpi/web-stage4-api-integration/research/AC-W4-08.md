# Research: AC-W4-08 — Mark as done: optimistic update + rollback on failure

## Understanding

When a user clicks "Mark as done" (or "I've already done this") in the task detail view,
the task card must immediately show `complete` state (optimistic update) while the API call
runs in the background. If the API call fails: the task snaps back to its previous state and
a toast notification tells the user their progress was not saved. If the API call succeeds,
GET /roadmap is re-fetched to sync the full task list from the server. After success, the
view navigates back to the roadmap list.

The verification scenario: mark a task → kill the API server → confirm rollback + toast →
restart API → retry → confirm success.

## Functions / Routes / Tests

**API client addition (`api.ts`):**
```typescript
export async function completeTask(taskId: string, token: string): Promise<void> {
  const res = await fetch(`${API_URL}/roadmap/tasks/${taskId}/complete`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${token}` },
  })
  if (!res.ok) throw new Error(`Complete task failed: ${res.status}`)
}
```

**Zustand store (`roadmapStore.ts`):**
```typescript
interface RoadmapStore {
  tasks: TaskListItem[]        // flat list for optimistic updates
  token: string                // stored so completeTask action can call API
  setRoadmap: (tasks: TaskListItem[], token: string) => void
  completeTask: (taskId: string) => Promise<void>
}
```
`completeTask` action:
1. Save `previousTasks = get().tasks`
2. `set({ tasks: tasks.map(t => t.taskId === taskId ? { ...t, cardState: 'complete', completedAt: now } : t) })`
3. Call `api.completeTask(taskId, token)`
4. On success: call `api.getRoadmap(token)` → remap → `set({ tasks: newTasks })`
5. On failure: `set({ tasks: previousTasks })` → trigger toast

**RoadmapView.tsx changes:**
- On mount: `roadmapStore.setRoadmap(allTasksFlat, token)` to seed store from SSR data
- Read `phases` by re-deriving from `roadmapStore.tasks` (or keep local phases derived from store tasks)
- Pass `onComplete={() => roadmapStore.completeTask(task.taskId)}` to `TaskDetail`
- After `completeTask` resolves (success): call `onBack()` to return to list

**TaskDetail.tsx changes:**
- Add `onComplete: () => Promise<void>` to `TaskDetailProps`
- Wire both "Mark as done" and "I've already done this" buttons to `onComplete`
- Add loading state during the async call (disable buttons, show spinner or "Saving…" text)

**Toast approach:**
- Build a minimal `useToast` hook + `ToastContainer` component in `src/components/ui/Toast.tsx`
  using `useState` + CSS transitions. Mounted in `(app)/layout.tsx`.
- OR install `sonner` (1 dependency, native Next.js App Router support, zero config).
  Decision: **install sonner** — it's the standard in the Next.js ecosystem, avoids building
  infrastructure for a solved problem, and AC-W4-14 will also need toast for error handling.

**No unit tests required for this AC** — the skill pattern and AC verification are manual
(mark task, kill API, retry). Integration behaviour is tested in AC-W4-16 Playwright E2E.

## Ambiguities / Questions

1. **Toast library**: No toast library is installed (`package.json` confirmed). The skill code
   shows `toast.error(...)` which implies a library. **Recommended: install `sonner`** — it's
   the de-facto standard for Next.js App Router and AC-W4-14 will also need it. Is this
   acceptable, or should we build a minimal inline component instead?

2. **Phase re-derivation**: Currently `RoadmapView` derives `phases` from `initialData.phases`
   via `mapApiPhasesToWeb`. After a re-fetch, the store holds flat `tasks`. The phase structure
   (phase num, name, timeline) comes from the API's `phases` array. The store should store
   the full `RoadmapApiResponse` (not just flat tasks) to allow full re-derivation.
   **Plan: store full API response, re-derive phases after re-fetch.**

3. **"I've already done this" button**: Same API call as "Mark as done"? The spec says
   "optimistic → API → re-fetch" as one flow for both. Treating both buttons as identical
   in behaviour (same endpoint, same optimistic update). Confirm?
