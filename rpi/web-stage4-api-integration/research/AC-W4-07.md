# Research: AC-W4-07 — Task detail populated from GET /roadmap/tasks/:taskId

## Understanding

When a user clicks a task row on the roadmap, `TaskDetail.tsx` opens. Currently it renders with
mock/static data. AC-W4-07 wires up a real `GET /roadmap/tasks/:taskId` fetch: the click triggers
an API call, the response is mapped to `TaskDetailData`, and all Layer 2 sections (steps, documents,
source card, tips) populate with real content.

The `TaskDetail.tsx` component and `TaskDetailData` type already exist from Stage 3. The work is:
1. Add `getTaskDetail()` to `api.ts` with the `TaskDetailApiResponse` type
2. Add `mapApiTaskDetail()` mapper in `roadmap-mapper.ts`
3. Wire up `RoadmapView.tsx` to fetch on click, update task with detail, re-render
4. Pass `token` from `page.tsx` to `RoadmapView` so the client component can make authenticated calls

## Functions / Routes / Tests

### `getTaskDetail(taskId: string, token: string): Promise<TaskDetailApiResponse>`
Add to `api.ts`. Fetches `GET ${API_URL}/roadmap/tasks/${taskId}` with Authorization header.
Throws with `status` attached on non-ok response.

### `TaskDetailApiResponse` (new type in `api.ts`)
Mirrors the backend `TaskDetailResponse` exactly:
```typescript
export interface TaskDetailApiResponse {
  taskId: string;
  name: string;
  status: 'NOT_STARTED' | 'IN_PROGRESS' | 'COMPLETE';
  isBlocked: boolean;
  estimatedDuration: string;
  processingTime: string | null;
  governmentSourceUrl: string;
  taskType: 'FREE' | 'PREMIUM';
  consequenceLine: string;
  steps: string[];
  documentsRequired: string[];
  commonMistakes: string[];
  watchOuts: string[];
  cost: string | null;
  relatedTasks: { taskId: string; name: string; relationship: string }[];
  professionalAdviceRequired: boolean;
  professionalAdviceNote: string | null;
}
```

### `mapApiTaskDetail(response: TaskDetailApiResponse): TaskDetailData`
Add to `roadmap-mapper.ts`. Key mapping decisions:

| API field | Web field | Mapping |
|-----------|-----------|---------|
| `steps: string[]` | `steps: TaskDetailStep[]` | `steps.map(s => ({ text: s }))` |
| `documentsRequired: string[]` | `documents: TaskDetailDocument[]` | `{ name, required: true }` for each |
| `governmentSourceUrl` | `source: TaskDetailSource` | parse URL hostname → agency; set url |
| `watchOuts + commonMistakes` | `tips: string[]` | concat both arrays |
| `whyNow` | _(not mapped)_ | API doesn't have this field; leave `whyNow` undefined |

For `TaskDetailSource.agency`: parse `new URL(governmentSourceUrl).hostname`, strip `www.` prefix,
use as agency name. e.g. `ird.govt.nz` → agency = `ird.govt.nz`, page = empty string.

### `RoadmapView.tsx` changes
- Add `token: string` prop
- Add `loadingDetailFor: string | null` state (holds taskId while fetching)
- On task click:
  ```
  setSelectedTask(task)             // show detail view immediately (detail = undefined → "coming soon")
  setLoadingDetailFor(task.taskId)  // optional: enables loading UI later (AC-W4-13)
  getTaskDetail(task.taskId, token) // fetch
    .then(res => setSelectedTask({ ...task, detail: mapApiTaskDetail(res) }))
    .finally(() => setLoadingDetailFor(null))
  ```
- On error: leave `selectedTask.detail` as undefined (shows fallback text) for now (AC-W4-14 adds proper error UI)

### `page.tsx` change
Add `token={session.access_token}` prop to `<RoadmapView>`.

### Verification
Manual: click any task on the roadmap → all Layer 2 sections populate with real content.
Network tab shows `GET /roadmap/tasks/:taskId` with 200 response.

## Ambiguities / Questions

**Resolved ambiguities (no blockers):**

1. **`whyNow` field absent from API**: The API has `consequenceLine` but not a separate `whyNow`. The amber callout already shows `task.consequenceLine`. Making `whyNow` optional in `TaskDetailData` and not populating it from the API removes the duplication. `TaskDetail.tsx` already conditionally renders all detail sections — the "Why now?" section simply won't show. This is correct: the amber callout IS the "why now" content.

2. **Loading state**: AC-W4-07 doesn't require a skeleton. The existing fallback text ("Detailed guidance coming soon.") serves as the transient state during the brief fetch. Skeletons are AC-W4-13's concern.

3. **Token access from client component**: Passing `token` from `page.tsx` is simpler than initializing a browser Supabase client. For MVP, the server-rendered token is fresh enough (1 hour expiry). Future sessions where the token expires mid-session are handled by Supabase middleware refresh.

4. **PREMIUM task 403**: If the API returns 403, the fetch fails → `detail` stays undefined → fallback text shows. AC-W4-14 adds proper error handling. For AC-W4-07, this is acceptable.
