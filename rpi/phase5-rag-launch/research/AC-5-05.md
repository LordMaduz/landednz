## Ambiguities / Questions

**1. Implementation order vs. AC number order:**
AC-5-05 (verification) is listed before AC-5-06 (code change), but implementation must be:
AC-5-06 first, AC-5-05 second. The plan and implementation will treat them as a paired unit:
implement AC-5-06 code change, then run the AC-5-05 manual test as verification of both.

**2. Error wrapping for `generateEmbedding()` — CONFIRMED ACTION REQUIRED:**
`embeddings.client.ts` does NOT wrap OpenAI errors as `AIFailureError` — they propagate raw.
`sendMessage()` sets SSE headers BEFORE the try block, so if `retrieveChunks()` throws a raw
OpenAI error, it re-throws to the global handler — a broken response (headers already sent, no
SSE error event emitted). This is a C13 violation.
**Fix:** Wrap the `retrieveChunks()` call in service.ts:
```typescript
try {
  retrievedChunksResult = await retrieveChunks({ ... })
} catch (error) {
  throw new AIFailureError(`RAG retrieval failed: ${error instanceof Error ? error.message : String(error)}`)
}
```
This converts any embedding/pgvector failure to `AIFailureError`, caught by the outer block → SSE error event → stream closes cleanly.

**3. GENERAL entry point — RAG with no taskContext:**
For GENERAL entry point (not TASK_CARD), the user asks any question. `retrieveChunks()` will
be called with `taskContext: null`. The task context boost step is skipped (existing behavior in
`retrieval.ts` step 5). The query embedding drives retrieval. This is correct behavior — confirming
there's no issue with null taskContext.

**4. consequenceLine source after RAG:**
`consequenceLine` is used in the system prompt (Component 2 task context section). In Phase 5,
this still needs to come from `TaskContentVariant` table (not from RAG chunks). The DB fetch for
`taskName` + `consequenceLine` must be preserved as a separate query when `taskContext` exists.
