## Functions / Routes / Tests

**SQL to run:**
```sql
CREATE INDEX ON "KnowledgeBaseChunk" USING ivfflat (embedding vector_cosine_ops);
```

**Verification query:**
```sql
SET enable_seqscan = off;
EXPLAIN SELECT id, "chunkKey", 1 - (embedding <=> '[0.1,0.2,...]'::vector) AS similarity
FROM "KnowledgeBaseChunk"
ORDER BY embedding <=> '[0.1,0.2,...]'::vector
LIMIT 5;
```

## Constraints That Apply

- **C05** — ivfflat MUST be created AFTER all embeddings are loaded. AC-5-01 is PASS (42/42). This is now safe.
- **C12** — cosine operator `<=>` used in the EXPLAIN query (not `<->` L2).
- **No code changes** — index is not in any migration file. It runs once manually after embeddings.

## Key Gotcha: Small Dataset and Query Planner

**42 rows is tiny.** PostgreSQL's query planner may choose a sequential scan over the ivfflat index because for 42 rows, a seq scan is genuinely faster. This does NOT mean the index failed — it means the planner is correct.

**To verify the index was created correctly**, use `SET enable_seqscan = off` in the session before running EXPLAIN. This disables the planner's ability to choose a seq scan, forcing it to use the index — proving the index exists and is functional.

This is the standard verification approach for pgvector indexes on small datasets.

In production (where this DB will have far more rows), the planner will naturally choose the index without needing `enable_seqscan = off`.
