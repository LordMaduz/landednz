# Research: AC-4-03 — SSE stream does not buffer, chunks arrive progressively in iOS simulator

## Understanding

AC-4-03 verifies that the SSE streaming endpoint delivers chunks **progressively** to clients — not as a single buffered payload after the entire Claude response is complete. The spec calls out two specific mechanisms:
1. `reply.raw.setTimeout(0)` — prevents Railway's 30s proxy timeout from killing long-running streams
2. No buffering — each `text_delta` from Claude must reach the client as it arrives

The code for this AC is mostly already in place from AC-4-02 (`reply.raw.write()` per chunk, `reply.raw.setTimeout(0)`). The gaps are:
- Missing `Connection: keep-alive` header — required for HTTP/1.1 SSE keep-alive
- Missing `X-Accel-Buffering: no` header — prevents nginx/Railway proxy buffering
- No progressive-delivery verification (existing `messages.test.ts` uses `app.inject()` which buffers the full response — cannot prove progressive delivery)
- No automated test that consumes chunks as they arrive (needed to prove the AC)

**Verification approach**: A Node.js script using `fetch()` with streaming reads (`response.body.getReader()`) against the running local server, logging timestamps per chunk. This is the only way to prove chunks arrive progressively (not via `app.inject()`). Manual iOS simulator test is the final gate step.

## Ambiguities / Questions

1. **What constitutes "pass" for automated verification?** The spec says "chunks arrive progressively in iOS simulator" — this implies a manual test. But should there also be an automated streaming script committed to the repo? My assumption: yes, a script is needed as automated evidence alongside the manual iOS simulator check.

2. **Does the `Connection: keep-alive` header matter for HTTP/2?** Railway and local dev both support HTTP/1.1 for SSE. This header is safe to add and is the standard for HTTP/1.1 SSE.

3. **Is `X-Accel-Buffering: no` in scope for Phase 4?** The spec mentions "iOS simulator" (local dev), not Railway. But it's zero-risk to add this header now rather than chase a production buffering bug in Phase 5.

None of these ambiguities block planning — my proposed approach handles all cases with minimal risk.
