# Research: AC-4-04 — CRISIS_SIGNAL detection leads response with Lifeline NZ

## Understanding

`level1.ts` is currently a stub returning no flags. AC-4-04 implements the
**CRISIS_SIGNAL** detection branch: when a user message matches crisis-distress
patterns, `runLevel1Guardrail()` returns `CRISIS_SIGNAL` in `flags` and a
pre-built Lifeline NZ augmentation string in `augmentations`.

That augmentation is injected into Component 3 of the system prompt (step 5 of
the 10-step pipeline). The instruction forces the model to output the Lifeline NZ
resource **before** any settlement information. This ordering is constitutional
constraint C08 — non-negotiable.

The AC test input is `"I can't cope with all this"` — this must match CRISIS_SIGNAL
and cause the SSE response to open with the Lifeline NZ text and phone number
(0800 543 354) before any settlement content.

Verification at unit level: `runLevel1Guardrail("I can't cope with all this")`
returns `{ triggered: true, flags: ['CRISIS_SIGNAL'], augmentations: [<Lifeline string>] }`.
Verification at integration level: send the message to a running server, confirm
response leads with Lifeline NZ.

## Functions / Routes / Tests

**`runLevel1Guardrail(content: string): GuardrailResult`** — replace stub:
- Lowercase the input for case-insensitive matching
- Check against CRISIS_SIGNAL patterns (substring match)
- If matched: `triggered: true`, `flags: ['CRISIS_SIGNAL']`, `augmentations: [<Lifeline string>]`
- If not matched: return existing stub shape (other flags stubbed for subsequent ACs)

**CRISIS_SIGNAL patterns** (from spec Appendix D + ai-guardrails skill):
```
"don't know what to do", "can't cope", "want to give up", "can't go on",
"overwhelmed", "end it all", "end it", "give up everything",
"can't handle this", "want to go home"
```

**CRISIS_SIGNAL augmentation string** (verbatim — do not paraphrase):
```
CRISIS RESOURCE — RESPOND WITH THIS FIRST, BEFORE ANY OTHER INFORMATION:
"It sounds like you're going through a really difficult time. Settling in a new
country is genuinely hard — you're not alone in finding it overwhelming.
If you need someone to talk to, Lifeline NZ is available 24/7: 0800 543 354.
They're experienced with exactly this kind of transition."
After providing this resource, you may then address any settlement question.
```

## Ambiguities / Questions

**One question on augmentation string ownership:** The augmentation string is a
literal used by the classifier to tell Claude what to say. Should it live as a
constant in `level1.ts`, or in `core/prompts/registry.ts`?

My reading: C04 says "prompt strings" (i.e., the assembled prompt sent to the API)
live in the registry. The augmentation constant is a classifier output that feeds
**into** the registry — it's guardrail domain knowledge, not a prompt build concern.
Placing it in `level1.ts` as a `const CRISIS_AUGMENTATION = '...'` is correct.

This matches the existing architecture: `buildChatSystemPrompt()` receives
`guardrailAugmentations: string[]` as a parameter — it assembles them, it doesn't
define them.

**No other ambiguities.** Patterns, augmentation string, and test cases all specified
exactly in the spec Appendix D and ai-guardrails skill.
