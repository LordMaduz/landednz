# Research: AC-2-07 — POST /roadmap/tasks/:taskId/complete → updated topThree

## Understanding

AC-2-07 implements task completion for the roadmap. When a user marks a task done:
1. Their `UserRoadmapEntry` status is updated to COMPLETE with a timestamp and `USER_MARKED` method
2. `getAffectedTasks()` finds the task's direct dependents (all dep types)
3. Only those affected tasks are recomputed (targeted — not full roadmap regeneration)
4. Returns: updated task status, new topThree, and which tasks just became unblocked

AC-2-08 is verified by the same route — it's a second test scenario that specifically checks the HARD dependency unblocking behaviour (a task that was isBlocked=true becomes unblocked when its prerequisite completes).

Both ACs are implemented in the same session: same service function, same route, two test scenarios.

## Functions / Routes / Tests

### Route contract (spec §4.3.3)

```typescript
POST /roadmap/tasks/:taskId/complete
Authorization: Bearer <jwt>
// Request body: none

// Response 200:
interface TaskCompleteResponse {
  taskId: string;
  status: "COMPLETE";
  newTopThree: RoadmapTask[];     // Recalculated top 3 after completion
  unlockedTasks: string[];        // Task IDs that transitioned isBlocked=true → false
}

// Error 404: task not in user's roadmap
// Error 409: task already COMPLETE
```

### Service: completeTask()

```typescript
async function completeTask(
  userId: string,
  taskId: string,
  currentDate: Date = new Date(),
): Promise<TaskCompleteResponse>
```

**Steps:**
1. Fetch `UserRoadmapEntry` for (userId, taskId) → 404 `TASK_NOT_FOUND` if absent
2. If `entry.status === COMPLETE` → 409 `TASK_ALREADY_COMPLETE`
3. Update entry: `status=COMPLETE`, `completedAt=currentDate`, `completionMethod=USER_MARKED`
4. Fetch `UserProfile` for userId → 404 `PROFILE_NOT_FOUND` if missing
5. Fetch all `UserRoadmapEntry` records (to build updated completedTaskIds set including new completion)
6. Fetch all `TaskDependency` records (for getAffectedTasks call)
7. Call `getAffectedTasks(taskId, allDependencies)` → affected task IDs (direct dependents)
8. For each affected task:
   - Fetch task basePriority, phase
   - Recompute `isBlocked` via `resolveBlockedTasks()` using updated completedTaskIds
   - Recompute `priorityScore` via `scoreTask()`
   - Update `UserRoadmapEntry` with new values
   - Track if `isBlocked` transitioned `true → false` (contributes to `unlockedTasks`)
9. Call `getRoadmap(userId)` to get updated topThree (reuses proven topThree logic)
10. Return `{ taskId, status: 'COMPLETE', newTopThree: roadmap.topThree, unlockedTasks }`

## Ambiguities / Questions

### ✅ RESOLVED: AC-2-08 scenario uses incorrect dependency assumption

**The spec states:** "POST /roadmap/tasks/:taskId/complete for T07 results in T08 appearing in the next topThree (hard dependency resolved)."

**The problem:** Pre-analysis Section 6 Issue 1 confirmed T07→T08 is **SOFT**, not HARD. Completing T07 does NOT unblock T08 — T08 was never blocked by T07. The scenario as written is impossible.

**Why this happened:** The spec was written before the T07→T08 SOFT dep correction.

**Two valid alternatives for how to test AC-2-08:**

**Option A — Use T06→T07 (actual HARD dep):**
Scenario: Day 2, no completions. T07 is blocked (score 75, not in topThree). Complete T06. T07 becomes unblocked (score 125), appears in topThree.
- Test verifies: `POST /roadmap/tasks/T06/complete` → T07 in newTopThree with `isBlocked=false`
- `unlockedTasks` contains 'T07'

**Option B — Use T07→T11 (also a HARD dep):**
Scenario: Day 2, T06 already complete. T11 is blocked (HARD dep on T07). Complete T07. T11 becomes unblocked, potentially appears in topThree.
- Test verifies: `POST /roadmap/tasks/T07/complete` → T11 in newTopThree (if score qualifies) with `isBlocked=false`
- `unlockedTasks` contains 'T11'
- This preserves the "completing T07 unblocks something" framing, just not T08

**Which option to use?**

Option A is cleaner: fewer tasks needed in the test DB, direct Golden1 connection, T06→T07 is the primary HARD dep in the dependency graph.

Option B preserves completing T07 as the action but changes what gets unblocked.

**RESOLUTION CONFIRMED:** Use Option A for AC-2-08 test scenario.
