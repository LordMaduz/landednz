# Research: AC-2-10 — GET /roadmap/tasks/:taskId — 403 for PREMIUM task, unsubscribed user

## Understanding

Build `GET /roadmap/tasks/:taskId` — the task detail endpoint (Layer 2 expansion).
AC-2-10 only verifies the **403 gate**: a PREMIUM task + no active subscription → 403 `PREMIUM_REQUIRED`.
The 200 path (full `TaskDetailResponse`) must also be implemented so the route exists and works for FREE tasks.

Auth required. Route logic:
1. Verify task is in user's roadmap → 404 if not
2. If `task.taskType === 'PREMIUM'`: check `Subscription.isActive` → 403 if no active sub
3. Otherwise: assemble `TaskDetailResponse` from Task + TaskContentVariant (personaKey match) + UserRoadmapEntry

## Functions / Routes / Tests

**Route:** `GET /roadmap/tasks/:taskId` — auth preHandler

**Service function:** `getTaskDetail(userId, taskId): Promise<TaskDetailResponse>`
1. Fetch UserRoadmapEntry (includes task + contentVariants) → 404 TASK_NOT_FOUND if absent
2. If `task.taskType === 'PREMIUM'`: `db.subscription.findUnique({ where: { userId } })` → if `!sub || !sub.isActive` → throw `AppError('PREMIUM_REQUIRED', ..., 403)`
3. Select variant: personaKey match → fallback to `solo_aewv`
4. Return `TaskDetailResponse`

**Tests (integration against real DB):**
- FREE task, no subscription → 200
- PREMIUM task, no subscription → 403 `PREMIUM_REQUIRED`
- PREMIUM task, subscription `isActive: false` → 403
- PREMIUM task, subscription `isActive: true` → 200
- Task not in roadmap → 404 `TASK_NOT_FOUND`

AC verification: the 403 case is what REQUEST.md requires.

## Schema Discrepancy — CRITICAL

`TaskDetailResponse` in spec §4.3.5 includes fields not present in the current `TaskContentVariant` Prisma model:

| Field | In spec | In Prisma `TaskContentVariant` |
|-------|---------|-------------------------------|
| `watchOuts` | `string[]` | **MISSING** |
| `relatedTasks` | `{ taskId, name, relationship }[]` | **MISSING** (would need a join model) |
| `professionalAdviceRequired` | `boolean` | **MISSING** |
| `professionalAdviceNote` | `string \| null` | **MISSING** |

**Two options:**

**Option A — Add scalar fields now (migration), defer relatedTasks:**
- Add `watchOuts String`, `professionalAdviceRequired Boolean @default(false)`, `professionalAdviceNote String?` to `TaskContentVariant` schema
- Run `prisma migrate dev`
- Return `relatedTasks: []` (empty — no join model, defer to v2)
- Pros: schema accurate for content seeded in AC-2-15; correct types flowing through from now
- Cons: small migration scope added to AC-2-10

**Option B — Return all defaults, defer schema changes:**
- Don't touch schema
- Return `watchOuts: [], relatedTasks: [], professionalAdviceRequired: false, professionalAdviceNote: null`
- AC-2-10 passes (only verifies 403 case)
- Schema gaps addressed when AC-2-15 seeds the KB
- Cons: `TaskDetailResponse` fields won't be populated even after AC-2-15 seeds content — requires a follow-up migration then

Option A is cleaner: adding 3 scalar fields to the Prisma schema is a small migration, and means AC-2-15 can populate them immediately. `relatedTasks` stays as `[]` (no join model in MVP scope — spec §2.3 shows it's a content field, not a Prisma relation).

**Decision needed:** Option A or B?
