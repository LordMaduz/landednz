# Research: AC-2-05 — POST /onboarding/profile creates UserProfile + all RoadmapEntries

## Understanding

AC-2-05 requires implementing the onboarding profile route: `POST /onboarding/profile`.
This route is the entry point to the roadmap engine — it takes the user's 5 onboarding
answers, creates a `UserProfile` record, runs the full roadmap generation pipeline
(filter → resolve → score), and creates one `UserRoadmapEntry` per applicable task.

The roadmap is generated synchronously — the route does NOT return until all entries
are written to the DB. The route returns 201 with the profileId, personaKey, and
`roadmapGenerated: true`.

The route requires a valid JWT (Bearer header). The pipeline calls:
1. `filterApplicableTasks()` — removes tasks not applicable to this persona
2. `resolveBlockedTasks()` — determines which tasks have unmet HARD deps
3. `scoreTask()` — computes priorityScore for each task

All three functions are pure functions already implemented in `core/`.

## Ambiguities / Questions

### 1. arrivalDate derivation — EXACT formula unknown (MUST RESOLVE before plan)

The spec states arrivalDate is "derived from arrivalTiming" for non-PRE_ARRIVAL timings,
but does NOT specify the exact date to use. The scoring formula depends on `arrivalDate`
for time urgency calculations.

The enum comments give windows, not exact dates:
- `RECENT` = "last 2 weeks"
- `WEEKS_TWO_TO_EIGHT` = "2–8 weeks ago"
- `OVER_TWO_MONTHS` = "more than 2 months ago"

**Options:**
- A: Use midpoint of each window (RECENT → 7 days ago, WEEKS_TWO_TO_EIGHT → 35 days ago, OVER_TWO_MONTHS → 90 days ago)
- B: Use the start of each window (RECENT → 1 day ago, WEEKS_TWO_TO_EIGHT → 14 days ago, OVER_TWO_MONTHS → 60 days ago)
- C: Use the end of each window (RECENT → 14 days ago, WEEKS_TWO_TO_EIGHT → 56 days ago, OVER_TWO_MONTHS → null/unknown)
- D: Use a specific "canonical" value defined in the spec (not found — may be in a skills file)

**Impact on scoring:** RECENT at 7 days vs 14 days produces different urgency bonuses. For T07 (bank), the Days 1-3 bonus ends at 3 days — choosing 7 days vs 1 day changes whether the bonus fires.

**Question for human:** What exact `arrivalDate` should be stored for each non-PRE_ARRIVAL timing? Options A/B/C above, or a different formula?

### 2. Auth middleware — inline or shared? (MUST RESOLVE before plan)

AC-1-08 implemented JWT extraction inline in `auth.route.ts`. AC-2-05 also requires JWT
auth. This is the second route needing auth — and AC-2-06 through AC-2-11 will also need it.

**Options:**
- A: Create `shared/middleware/auth.ts` now — reusable Fastify preHandler hook that extracts userId and attaches to `request` — clean pattern for all future routes
- B: Inline JWT extraction in `onboarding.route.ts` — copy the pattern from auth.route.ts — quick but creates duplication

**Recommendation:** Option A (create shared middleware now) avoids copy-paste across all
future routes and is the cleaner approach. But this touches `auth.route.ts` refactor
territory — need human sign-off before doing that.

### 3. VALIDATION_ERROR and PROFILE_EXISTS not in ErrorCode enum

Current `shared/errors.ts` ErrorCode union does not include `VALIDATION_ERROR` or
`PROFILE_EXISTS`. These must be added. This is a minor change, not an ambiguity —
listing for awareness. Will add to plan as a file modification.
