# Research: AC-2-09 — POST /roadmap/bulk-override correct topThree

## Understanding

AC-2-09 implements bulk task completion — for users who completed NZ settlement tasks before discovering LandedNZ (e.g., they already have a bank account and IRD number). A single request marks multiple tasks COMPLETE at once using `BULK_OVERRIDE` as the completion method.

Key difference from `completeTask()` (AC-2-07):
- **Multiple tasks** marked in one request
- `completionMethod: BULK_OVERRIDE` (not `USER_MARKED`)
- **Full roadmap recomputation** after all overrides applied — not targeted per-task. Multiple completions can have cascading dependency effects that targeted recomputation would miss.
- **No error** if a task is already COMPLETE — silently add to `skipped`

## Functions / Routes / Tests

### Route contract (spec §4.3.4)

```typescript
POST /roadmap/bulk-override
Authorization: Bearer <jwt>

// Request body:
interface BulkOverrideRequest {
  completedTaskIds: string[];
}

// Response 200:
interface BulkOverrideResponse {
  marked: string[];      // Task IDs successfully marked COMPLETE in this request
  skipped: string[];     // Task IDs already COMPLETE — skipped without error
  newTopThree: RoadmapTask[];
}

// No errors thrown for already-complete tasks — silently skip
```

### Service: bulkOverride()

```typescript
async function bulkOverride(
  userId: string,
  taskIds: string[],
  currentDate: Date = new Date(),
): Promise<BulkOverrideResponse>
```

**Steps:**
1. Fetch all `UserRoadmapEntry` for userId (to identify which requested IDs are in roadmap and which are already COMPLETE)
2. Separate requested taskIds into:
   - `toMark`: in roadmap AND not COMPLETE
   - `skipped`: in roadmap AND already COMPLETE
   - silently ignore: not in roadmap at all
3. Bulk mark `toMark` entries: `status=COMPLETE`, `completedAt=currentDate`, `completionMethod=BULK_OVERRIDE`
4. Fetch `UserProfile` (for personaKey, arrivalDate)
5. Fetch all UserRoadmapEntry (fresh — reflects new completions)
6. Build `completedTaskIds` set
7. Fetch all Tasks with HARD dependencies for user's roadmap
8. **Full recomputation** — for every non-COMPLETE entry:
   - `resolveBlockedTasks()` → new isBlocked
   - `scoreTask()` → new priorityScore
   - Update UserRoadmapEntry record
9. Call `getRoadmap(userId)` for updated topThree
10. Return `{ marked: toMark, skipped, newTopThree: roadmap.topThree }`

## Ambiguities / Questions

### ✅ RESOLVED: Handling task IDs not in the user's roadmap

**Human confirmation:** Use Option A (silently ignore).

Task IDs not in the user's roadmap are silently ignored — they don't appear in `marked` or `skipped`. This keeps `skipped` semantically clean per spec ("already COMPLETE"). Invalid task IDs are typically system/developer issues (UI bugs, stale data), not user errors, so users shouldn't see them in the response.
