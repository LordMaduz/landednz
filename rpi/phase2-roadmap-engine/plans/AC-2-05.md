## Approach

AC-2-05 builds the entry point to the roadmap engine. Three layers:

**1. Shared auth middleware** (`shared/middleware/auth.ts`): A reusable Fastify `preHandler` that extracts the Bearer JWT, verifies it via JWKS (same `jose` pattern from `auth.service.ts`), and attaches `userId` to the Fastify request via `decorateRequest`. Every future authenticated route (AC-2-06 through AC-2-11) uses this instead of copy-pasting JWT extraction.

**2. Onboarding service** (`features/onboarding/onboarding.service.ts`): Orchestrates the pipeline — validates arrivalDate, checks for duplicate profile (409), creates `UserProfile`, fetches all `Task` records from DB, calls `filterApplicableTasks()` → `resolveBlockedTasks()` → `scoreTask()` (all already implemented in `core/`), then bulk-creates `UserRoadmapEntry` records via `createMany()`.

**3. Onboarding route** (`features/onboarding/onboarding.route.ts`): Thin — applies auth preHandler, delegates to service, returns 201.

Tests are integration tests that call `createProfile()` directly against the real Docker postgres DB. Service accepts `userId` (already extracted by middleware), so no JWT needed in tests.

## Test Strategy

Integration tests calling `createProfile()` directly against real Docker postgres (no HTTP, no JWT):

**Test setup:** Create test `User` and a handful of test `Task` records (with different `applicableFamilySituations`) as fixtures. Clean up with `afterEach`.

| # | Scenario | Expected |
|---|----------|----------|
| 1 | Solo AEWV + past arrivalDate | UserProfile created, entries = applicable tasks only |
