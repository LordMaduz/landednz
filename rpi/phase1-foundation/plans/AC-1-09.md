# Implementation Plan: AC-1-09

## Approach
AC-1-09 (invalid JWT → 401) was implemented as the error path of the same `POST /auth/verify` handler built for AC-1-08. No additional files are required. The route handler checks for missing/malformed Authorization headers and throws `AppError('INVALID_TOKEN', message, 401)` before reaching the service. The service catches all `jose` JWKS/JWT errors (JWTExpired, JWSInvalid, etc.) and wraps them as `AppError('INVALID_TOKEN', 'Invalid or expired JWT token', 401)`. Missing required claims (`sub`, `email`) are also validated as INVALID_TOKEN. All AppErrors propagate to the global error handler which serialises them as `{ error: "INVALID_TOKEN", message: "..." }` with HTTP status 401.

## Error Scenarios Covered

| Scenario | Where handled | Response |
|----------|---------------|----------|
| Missing Authorization header | `auth.route.ts` | 401 `INVALID_TOKEN` |
| Invalid Bearer format | `auth.route.ts` | 401 `INVALID_TOKEN` |
| JWT signature invalid | `auth.service.ts` — jose catch | 401 `INVALID_TOKEN` |
| JWT expired | `auth.service.ts` — jose catch | 401 `INVALID_TOKEN` |
| JWT missing `sub`/`email` | `auth.service.ts` — claims check | 401 `INVALID_TOKEN` |
