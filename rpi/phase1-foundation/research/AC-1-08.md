# Research: AC-1-08 — POST /auth/verify valid JWT → 200 correct fields

## Understanding

Build the `POST /auth/verify` endpoint — the bridge between Supabase Auth and our
application database. The mobile app calls this on every launch after login, passing
the Supabase JWT in the Authorization header. The endpoint:
1. Verifies the JWT using ES256 JWKS (NOT shared secret — see session note)
2. Extracts userId (JWT `sub` claim) and email from the verified token
3. Creates the User record in our DB if it doesn't exist (upsert)
4. Checks if a UserProfile exists for that user
5. Returns `{ userId, email, isNewUser, hasProfile }`

Second call for the same user returns `isNewUser: false` (upsert idempotency).

AC-1-09 (invalid JWT → 401) is the error path of the same handler — implementing
both together in one unit.

## Critical: Spec vs Reality Mismatch

The spec (§3.2.2) says:
```
// - JWT must be verified against SUPABASE_JWT_SECRET
```

**This is WRONG for Supabase CLI v2.** As captured in session notes (AC-1-05):
- Supabase CLI v2.75.0 uses ES256 (ECDSA P-256), not HS256
- There is no `SUPABASE_JWT_SECRET`
- Verification MUST use JWKS endpoint discovery via `jose` library
- JWKS local: `http://127.0.0.1:54321/auth/v1/.well-known/jwks.json`
- JWKS production: `https://[project-ref].supabase.co/auth/v1/.well-known/jwks.json`

## Functions / Routes / Tests

### Route: `POST /auth/verify`
```typescript
// Request headers: Authorization: Bearer {supabase_jwt}
// Request body: none

// Response 200:
{ userId: string, email: string, isNewUser: boolean, hasProfile: boolean }

// Response 401 (AC-1-09):
{ error: "INVALID_TOKEN", message: string }

// Response 500:
{ error: "INTERNAL_ERROR", message: string }
```

### Service: `verifyAndUpsertUser(token: string)`
```typescript
// 1. Verify JWT using JWKS — jose library
const JWKS = createRemoteJWKSet(new URL(`${config.supabaseUrl}/auth/v1/.well-known/jwks.json`))
const { payload } = await jwtVerify(token, JWKS)

// 2. Extract claims
const userId = payload.sub           // Supabase user UUID
const email = payload.email          // user email

// 3. Upsert User in our DB
const { user, created } = await upsertUser(userId, email)

// 4. Check UserProfile existence
const hasProfile = await db.userProfile.count({ where: { userId } }) > 0

// 5. Return
return { userId, email, isNewUser: created, hasProfile }
```

### User Upsert Pattern
```typescript
// upsert: create if not exists, return existing if already there
// Prisma upsert on the primary key (userId from Supabase JWT sub)
const user = await db.user.upsert({
  where: { id: userId },
  create: { id: userId, email },
  update: {},  // no update — User record is immutable after creation
})
// isNewUser = true if createdAt === updatedAt (or track via $transaction)
```

Since Google OAuth isn't set up yet, we need a test JWT. Two options:

**Option A (recommended):** Create a test user via Supabase Studio
1. Open `http://127.0.0.1:54323` → Authentication → Users
2. Create user with email + password
3. Use `supabase.auth.signInWithPassword()` to get a JWT
4. Use that JWT to test the endpoint

**Option B:** Use the Supabase admin API directly
```bash
curl -X POST http://127.0.0.1:54321/auth/v1/token?grant_type=password \
  -H "apikey: {anon_key}" \
  -H "Content-Type: application/json" \
  -d '{"email":"test@test.com","password":"password123"}'
```

**Verification checks:**
- AC-1-08: `curl -H "Authorization: Bearer {valid_jwt}" POST /auth/verify` → 200 with correct fields. Second call → `isNewUser: false`
- AC-1-09: `curl -H "Authorization: Bearer invalid_token" POST /auth/verify` → 401
